# Necro experiment retrospective and corrective plan

Date: 2026-09-21. Scope: the initial Qwen3.5-0.8B baseline, the pilot and subsequent local experiments, Phases 2 through 5, and the unified cloud primary run. Project status: abandoned.

I am abandoning this attempt to build a stable Jev-like judgment model. Insufficient experimental experience led to repeated design and review failures, enormous expenditure, and an enormous investment of time and effort without delivering the intended release. The project failed its objective completely. Its twenty completed training runs still provide useful evidence, including substantial gains from LoRA, and that evidence should remain available for other people to reproduce and examine.

The most serious mistake was repeatedly advancing from a narrow improvement to another training intervention before checking whether the training distribution and development evidence represented the intended capability. Class coverage, condition wording, semantic eligibility, numerical relations, and number representation were audited at different times, usually after a failure exposed the missing dimension. The accumulated process was reactive. Its documentation became more elaborate faster than its ability to catch the next data defect.

I also made avoidable judgment errors. I allowed Jev comparisons to influence how I described the objective, although the actual objective was a strong, stable 0.8B model that improves overall on Phase 4. I gave too much attention to apparent GPU slowness before normalizing the workload. I treated fixed hyperparameters as a sufficient experimental plan without preserving the intermediate checkpoints needed to assess training duration. I accepted audit outputs whose coverage assumptions I had not independently challenged. These decisions consumed compute, attention, and confidence in the project.

The technically justified recovery path would retain LoRA, repair the data and validation design, and use a bounded experiment with useful intermediate evidence. That path is documented for independent reproduction and future research. This project is closed, and no further training is scheduled. Continuing the same frozen dataset at another learning rate would answer too little. Declaring the model's capacity exhausted would also go beyond the experiment, because basic coverage defects remain unresolved.

## 1. The objective that should have governed the work

Necro is intended to provide compact, local, typed judgments across eight task families. Its value comes from useful accuracy, reasonable probability estimates, predictable behavior, low operational overhead, and a package that actually works through the intended SDK and HTTP interface. A model that improves a headline average while repeatedly rejecting valid records does not meet that objective. A model that performs well in a notebook but changes behavior after export is also unfinished.

The final target was overall improvement over the Phase 4 reference, with small, explicit task tradeoffs and no major systematic condition defect. The words overall and stable both matter. Overall permits a limited decline in one ordinary slice when broader gains justify it. Stable requires resistance to changes that should preserve meaning, including equivalent numeric representations, legitimate instruction paraphrases, option order, and combinations of gates and missing fields. It also requires a credible independent acceptance result and reliable deployment behavior.

The target never required defeating Jev. Jev is a useful external reference because it answers the same kind of typed questions and exposes where Necro remains weak. It is not the definition of success for a locally deployable 0.8B model. Treating every gap to Jev as a repair obligation encourages an open-ended project, especially when the models' training resources and serving conditions are not matched. The historical protocols did include Jev-relative acceptance thresholds. Those historical failures must remain recorded, while the final product objective must be stated correctly.

The request for a perfect version expressed a need for confidence after repeated regressions. I should have converted that need into concrete release behavior immediately. The useful interpretation is a version without known severe systematic failures inside a defined operating scope, with bounded ordinary errors and honest limitations. Answering that request with either a guarantee of perfection or a generic statement that all models make mistakes would evade the engineering work. The work is to define which errors are unacceptable, measure them, and refuse promotion when they remain.

The checkpoint terminology also needs precision. Throughout most project records, base means the official post-trained Qwen/Qwen3.5-0.8B without a project adapter. A separate pretraining-only Base checkpoint exists and was deferred. These are different starting points. The official repositories distinguish the [post-trained model](https://huggingface.co/Qwen/Qwen3.5-0.8B) and the [pretraining-only Base model](https://huggingface.co/Qwen/Qwen3.5-0.8B-Base). All project-specific comparisons below identify the actual artifact and cohort.

## 2. What the comparisons establish

A single table ranking every phase by its reported percentage would be misleading. Different phases used different tasks, source distributions, calibration procedures, and exposure histories. The first pilot's validation accuracy cannot be compared directly with the later eight-task macro. Historical local inference and the cloud rerun also produced slightly different values on some identical requests. Those differences must remain visible rather than being silently rounded into one supposed canonical score.

| Evaluation cohort | Compared artifact | Necro result | Jev 1.13.0 result | Role at the time |
|---|---|---:|---:|---|
| Initial 400 public questions | Official checkpoint, no LoRA | 35.25% accuracy | 84.75% | Diagnostic validation, later regression |
| Same initial 400 questions | Pilot LoRA | 69.50% accuracy | 84.75% | Exposed regression |
| Phase 1, 374 questions | Selected round3 | 78.61% accuracy | 81.28% | Test opened after selection |
| Phase 2, 1,171 questions | Operator-contrast seed2026 | 80.98% task macro | 90.62% | Independent test at that stage |
| Phase 3, 1,790 questions | Instruction seed2026 | 86.34% task macro | 92.34% | Independent test at that stage |
| Same 1,790 questions | Phase 4 selected repair | 89.43% task macro | 92.34% | Exposed multi-task regression |
| Phase 4, 720 conditions | Phase 4 selected repair | 91.94% accuracy | 98.33% | Independent condition test at that stage |

The broad historical pattern supports adaptation. The official checkpoint was poorly aligned with the project's direct candidate-scoring interface. The pilot and later adapters made large improvements. The narrower question of whether each new stage improved the preceding model needs paired comparisons on identical requests. That requirement becomes more important as gains shrink from tens of percentage points to fractions of a point.

The historical 1,790-question comparison provides one such view. The Phase 2 predecessor scored 87.25% task macro, the Phase 3 instruction parent 86.34%, and Phase 4 89.43%. Jev scored 92.34%. Phase 3 improved intent and reading while substantially damaging numeric precondition handling. Phase 4 recovered much of that numeric behavior and improved the aggregate, then failed a separate condition transfer check. This is a sequence of meaningful gains and meaningful regressions, not steady progress toward a uniformly stronger model.

The cloud environment recomputed its own baselines. On the same exposed eight-task cohort, the official model scored 49.1483%, the instruction parent 86.4174%, Phase 4 89.5660%, and the unified primary 89.8303%. The primary's gain over Phase 4 was only 0.2644 percentage points, with a paired source-group 95% interval spanning approximately -1.09 to +1.66 points. Jev was not rerun as part of this cloud comparison. Its historical result belongs in the historical table, not in a claim about a newly measured cloud contest.

On the original eight-task development cohort, the cloud primary improved from Phase 4's 87.5021% to 89.7184%, a gain of 2.2163 points with a paired interval of approximately +0.67 to +3.89. That is encouraging development evidence. At the same time, complete condition accuracy collapsed to 58.33%. Reporting the development gain alone would conceal the result that determines whether the model can be used confidently.

Sources for these distinctions are the [baseline record](docs/process/baseline-2026-09-20.md), [Phase 1 report](docs/reports/improvement-2026-09-20.md), [Phase 2 record](docs/process/phase2-development.md), [Phase 4 validation](docs/process/condition-validation-2026-09-21.md), and [unified primary report](docs/reports/unified-primary-2026-09-21.md).

## 3. The initial interface work was necessary, but its claims needed limits

The initial baseline established an important separation between protocol correctness and judgment quality. The HTTP service could return a complete probability distribution through the official SDK while selecting the wrong answer. A 255-option request returned a distribution summing to one and still chose the wrong candidate. Passing schema checks, authentication checks, and response-shape checks therefore could not establish that the model understood the decision.

Prompt and label design had large effects. The early JSON wrapper with uniform letter labels scored 17 out of 24 development examples. Direct text prompts with Yes/No labels for Noul increased that to 22 out of 24. Large candidate sets exposed position bias when single-letter and multi-letter labels were mixed. Fixed-width two-letter labels did not clearly solve it. Full-sequence numeric-label scoring became the working approach, with shared input caching to control inference cost.

This work was legitimate. The project was building a specific interface, and a poorly chosen answer encoding could invalidate every later model comparison. The mistake would be to treat performance under that interface as a complete statement about the official model's general intelligence. A post-trained model answering through constrained label likelihoods is operating under a different procedure from ordinary generation, potentially with reasoning text or a different prompt. The baseline measures compatibility and ability within the chosen procedure together.

That qualification matters when deciding whether LoRA is worthwhile. The practical question is whether adaptation improves the system we intend to deploy. The existing evidence answers yes. A different question, whether an extensively optimized ordinary-generation baseline could match the adapter at the same latency and resource budget, has not been answered by this project. That unanswered alternative does not justify abandoning the measured gains, and it should not silently expand a recovery effort into a separate prompting research program.

The baseline latency measurements also needed careful interpretation. Local inference and a remote Jev API involve different network and service overheads. A local loopback result can establish that Necro serves a small request quickly on the recorded hardware. It cannot isolate the relative compute efficiency of two underlying models. This distinction was documented in the early report and should have remained equally strict when later comparing local and cloud training speed.

The initial 24 handcrafted examples were useful for development but too small and too exposed to justify broad conclusions. Their movement from 17 to 22 correct showed that the interface mattered. The 400 public questions then showed that the remaining weakness was much larger than those examples suggested. This was an early demonstration that a convenient local check can improve while general task performance remains poor. The later condition experiments repeated that pattern at a larger scale.

## 4. The pilot established value, then selection became inconsistent

The first LoRA experiment was a successful feasibility test. It used 994 English and Chinese examples, rank 16, alpha 32, dropout 0.05, a learning rate of 1e-4, effective batch eight, and one epoch. Training took 239.33 seconds. On the 200-question validation set, accuracy improved from 38.5% to 72.0%. The model corrected 96 errors and introduced 29, a net gain of 67 correct answers. Those paired transitions made the improvement concrete.

The pilot also completed useful runtime checks. Only adapter parameters were trainable. Disabling the adapter reproduced the original probe logits exactly. A fresh process loaded the adapter, and SDK/HTTP checks covered the response types and Chinese input. These checks supported the conclusion that the training and serving pipeline could produce a useful artifact. They did not establish eight-task stability, which was outside that pilot's evidence.

The subsequent rounds made the first methodological problems clearer. Round2 repeated the pilot data at 3e-5. Round3 used 2,336 examples at 5e-5 and started from the pilot. Round4 continued from round3 for another epoch at 2e-5. Development accuracy rose to 73%, 84%, and 85%, respectively. The selected release used round3 because round4's raw NLL looked worse. Only round3 then received calibration for the selected result.

That was an inconsistent comparison. When both candidates later received the same calibration procedure, round4 had better development accuracy, NLL, Brier, and ECE. Its calibrated NLL was 0.6450 against round3's 0.6601, and Brier was 0.2289 against 0.2369. A selection rule that penalized one model's raw confidence while evaluating the other's calibrated confidence did not compare the deployable systems fairly. The [design review](docs/process/design-review-2026-09-20.md) correctly recorded this error.

The parameter history also prevented clean explanations. Round3 changed data volume, mixture, templates, and learning rate. Round4 changed the seed and microbatch as well as the learning rate and accumulated training. It is reasonable to use such exploratory runs to find a useful candidate. It is unreasonable to extract a confident causal claim about learning rate from them. The project needed to distinguish candidate development from controlled experiments much earlier.

Data volume was overstated by presentation counts. Removing an irrelevant record identifier left only 36 distinct pilot rule requests and 33 expanded rule requests. Repeated presentations can legitimately reweight examples, but they do not create new semantic coverage. The later unified dataset's unique-request accounting was an improvement. Its failure shows that uniqueness alone also remains insufficient: thousands of distinct numbers can repeat the same incomplete relation structure.

The selected Phase 1 model reached 78.61% on 374 test questions, against Jev's 81.28%, with a broad paired interval around the difference. Its numerical boundary errors remained significant, including accepting an amount below a required threshold. The correct outcome was a useful early artifact with documented weaknesses. Treating that as evidence that a little more training would naturally produce a stable general judgment model would have gone beyond the measured result.

## 5. Phase 2 improved experimental control and still missed representation

Phase 2 expanded the work to eight families and introduced a controlled objective comparison. Answer-token cross-entropy and candidate-restricted cross-entropy started from common weights with common data and major hyperparameters. Answer CE reached 85.15% development task macro, candidate CE 84.90%, and later refinement 86.79%. The objective difference was small, with uncertainty spanning either direction. Keeping answer CE was a reasonable choice, supported by this comparison rather than by a preference for a more complicated loss.

Source isolation also became more rigorous. The supplementary audit found that retrieval question IDs were insufficient because different questions could share candidate documents. The earlier training and final retrieval slices shared 18 correct documents, or 49 documents when negative candidates were included. Three normalized paraphrase sentences also crossed evaluation boundaries. Connected source components were needed to link all relevant documents, sentences, premises, and translations. The corrected strict registration was established before final predictions were read.

That correction mattered. It protected the independent test from one form of leakage and preserved earlier registrations rather than rewriting history. However, the project began to rely too heavily on source separation as a general certificate of data quality. Independence and representativeness answer different questions. A source-disjoint development set can still omit half the classes or systematically favor a particular instruction structure. A clean split does not make an incomplete distribution complete.

Operator-contrast training produced one of the stronger local improvements. At 3e-5 for one epoch, the selected seed reached 89.13% strict-development macro, and the replication reached 89.10%. Numeric accuracy rose substantially. An additional reading-focused run offered only a small local reading gain and slightly worse macro, so it was not selected. This was a sensible use of a bounded comparison and a stopping decision.

Parameter averaging was also tried by averaging LoRA A and B factors from related runs. Its development Brier improved, while macro accuracy was below the selected seed. This was another candidate, not a guaranteed ensemble improvement. Averaging the factors separately introduces cross terms when their product is formed, so it is not generally equivalent to averaging the resulting full weight updates. The actual measured candidate therefore had to stand on its own results, as it did.

The independent Phase 2 test then reached only 80.98% macro against Jev's 90.62%. Intent fell to 51.50%. Reading-negation consistency was 30% on ten perturbation pairs. The subsequent audit found positive training coverage for only 31 of 60 intent classes and development coverage for only 20. Missing classes still appeared as negative candidates. Training could therefore repeatedly teach the model to reject categories it rarely or never saw as correct.

The earlier conclusion that lightweight improvements had reached diminishing returns was withdrawn. That withdrawal was necessary, and it should have changed the operating method for every later phase. Before invoking model limits or a search plateau, the project needed explicit coverage checks on the task's semantic alternatives. The most important failure in the later cloud run is that this lesson was documented and still not generalized to numeric relations.

The [source audit](docs/process/phase2-source-audit.md) and [coverage audit](docs/process/phase3-coverage-audit.md) describe these as separate defects. They should remain separate in future review because fixing one does not establish that the other has been checked.

## 6. Phase 3 corrected class coverage and amplified a different weakness

Phase 3 addressed a real data defect. Positive intent examples covered all sixty classes in both languages across training, development, and calibration. Sampling used broader source snapshots and structural exclusions. A wrong manual description of cooking_query was corrected using the source task's actual examples. This work improved the meaning of the training problem, not merely its size.

Coverage refinement used 4,076 records, one epoch, rank 16, learning rate 3e-5, and effective batch eight. On the same 1,464 development records, task macro improved from 85.97% to 87.37%. Intent improved from 74.15% to 79.83%, with a paired interval supporting the improvement. Numeric accuracy declined from 91.48% to 89.20%. The useful class-coverage result and the numeric regression should have been treated as equally important outcomes of the update.

Instruction refinement then addressed nested reading negation. The coverage model had zero consistency on ten development pairs asking about the negative answer proposition. Paired instruction training raised that consistency to 100% for seed2026 and 80% for seed2027. The selected seed achieved 87.98% development macro, while the replication reached 86.47%. The defect repair was encouraging, but the overall improvement was not reproduced across both seeds. That variability belonged in the selection decision, not only in an appendix.

The later numeric investigation exposed the damage concealed by aggregate development results. On the same 172 original-wording numeric records, the Phase 2 predecessor answered 146 correctly, coverage refinement 133, and instruction seed2026 122. Coverage lost thirteen previously correct answers without correcting another. Instruction refinement lost eleven more. All eleven additional errors from that final instruction stage involved a disabled gate. The numerical comparison was true, but the false gate should have made the record ineligible.

Changing only the rule wording to an equivalent if-and-only-if formulation restored all four compared checkpoints to 172 out of 172. Changing field names alone gave much smaller improvements. This was strong fixed-weight evidence of expression sensitivity. The development rules predominantly used the formulation on which the models performed well. Selection therefore rewarded behavior inside a familiar expression pattern while failing to detect deterioration on another legitimate formulation.

More replay had not fixed that gap. Coverage refinement replayed 532 numeric records from eighteen source groups. Instruction refinement increased replay to 970 records from thirty-five groups, but only sixty-eight involved disabled gates. Repeating more records from an incomplete distribution did not ensure retention of the missing behavior. This is the earlier version of the same mistake later made with the larger unified dataset: quantity was allowed to stand in for coverage.

A separate export defect also appeared. Reloading merged Phase 3 weights preserved all 1,790 argmax decisions but changed probabilities by up to 0.00279618, exceeding the registered 1e-5 tolerance. The investigation found matching weight tensors, buffers, and tokenization, then identified different parameter gradient flags between loading paths. Freezing parameters on every inference path eliminated the difference, and the full reload comparison subsequently reached zero maximum probability difference. SDK and real HTTP validation then completed for that Phase 3 artifact.

That loader correction is a verified engineering success. It must not be used as evidence that later Phase 4 or unified candidates completed release validation. Each artifact has its own capability and packaging state. The [numeric regression investigation](docs/process/numeric-regression-2026-09-21.md) records both the behavioral failure and the separate export correction.

## 7. Phase 4 repaired preconditions and introduced false rejection

Phase 4 began from the instruction parent with a focused precondition repair. The first run used 2,464 records at 1e-5 for one epoch. It raised original-wording numeric accuracy from 70.93% to 90.70%, with disabled gates improving from four correct out of forty to thirty-six. Missing fields remained weak at five out of twelve. Existing numeric development also fell outside the retention margin. This candidate failed for concrete reasons, and further work had a defined defect to address.

The second run added formulations and numeric replay, reaching 93.60% on the exposed numeric regression. Missing fields improved only to eight out of twelve. A cross-product audit then found an absent combination involving implicit guard-first wording, equality, a missing gate, and an otherwise true comparison. Marginal counts for missing fields had concealed the missing interaction. This was another lesson that checking each factor separately was insufficient.

The corrective matrix covered eight hundred registered combinations and generated 3,200 condition presentations. With replay, it trained on 4,756 presentations and 4,436 unique requests. The learning rate was reduced to 5e-6. The run repaired all forty original disabled-gate cases and all twelve missing-field cases, while the original numeric development remained four correct answers below the retained baselines. The resulting 2.27-point decline exceeded the two-point margin.

A controlled smaller-update comparison halved the learning rate to 2.5e-6 while preserving the data, parent, seed, and evaluation cohorts. Development macro improved slightly relative to the larger update, from 87.51% to 87.63%, while the numeric-development count stayed at 157 out of 176. The registered preliminary check still failed. The selection record accepted that particular tradeoff before opening the independent condition holdout and preserved the original failed assessment.

This distinction matters when interpreting the claim that lower learning rates had already worked better. There was real evidence of better aggregate retention in this narrow continuation comparison. There was no demonstrated recovery of the four-question numeric loss, and no evidence that the same learning rate should be transferred to a fresh adapter. The correct lesson was that update size deserves controlled measurement. It was not a universal recipe.

The independent condition holdout revealed a different serious defect. Phase 4 reached 91.94% overall, but complete records fell from the instruction parent's 99.58% to 84.17%. Chinese complete records fell from 99.17% to 74.17%. All thirty-eight complete-record errors were false rejections of eligible records. Improvements on disabled gates and missing fields raised the average enough to conceal the deterioration in ordinary qualifying cases.

The semantic audit explained an important flaw in the matrix. Only 320 of its 3,200 presentations were eligible. The other 2,880 were ineligible. Yes/No answers were exactly balanced because the question polarity varied, but the underlying scenario distribution was one eligible record for every nine ineligible records. An answer-label audit had been mistaken for an audit of the concept the model needed to learn.

This was not a minor accounting oversight. Eligibility was the behavior under repair. Its distribution should have been a primary audit dimension before generating or weighting the matrix. A matrix can be complete relative to a badly chosen set of axes and still train the wrong emphasis. The [Phase 4 validation](docs/process/condition-validation-2026-09-21.md) and [pre-release review](docs/reports/pre-release-2026-09-21.md) document the resulting release failure.

## 8. Phase 5 showed that semantic balancing was necessary to investigate and insufficient to finish

The first semantic-balance intervention was controlled loss weighting. Eligible matrix presentations received weight five and ineligible presentations weight five ninths, giving equal total contribution to the two semantic outcomes. Replay retained unit weights. The requests, labels, order, initial adapter, seed, optimizer steps, and effective batch size remained unchanged. The learning rate was 2.5e-6.

This was a better causal comparison than several earlier experiments. It directly tested a change to semantic weighting instead of adding another unrelated dataset or changing several optimizer settings. The implementation also handled an important detail correctly: weights were normalized over the dataset, not separately inside every microbatch. Tests checked that unequal microbatch accumulation preserved the intended gradients.

The result was a partial improvement and a failed candidate. Weighting repaired eleven of the thirty-eight known false rejections. Complete-record accuracy rose to 88.75%, and Chinese complete-record accuracy to 80%. English gate and missing-field performance remained below the requirements. The exposed eight-task macro was 89.5821%, but the condition and original numeric-development checks still failed. A good aggregate could not compensate for the unresolved core defect.

Physical resampling then changed presentation counts while keeping unit loss weights and the same learning rate. It balanced eligible and ineligible matrix presentations, preserved replay, and retained the registered training budget. The resampled matrix contained only 1,820 unique requests. Repeating those requests changed exposure frequency rather than introducing equivalent new coverage.

Resampling repaired ten of the thirty-eight known failures. Complete-record accuracy was 88.33%, and the Chinese complete slice was 78.33%. The short exposed condition screen failed, so the expensive full development, calibration, and eight-task assessment was not run. The 89.5821% macro belongs to the weighted candidate alone. Assigning it to resampling would falsely improve the evidence for an experiment that never received that evaluation.

New development examples also exposed inherited negative-number strict-comparison failures in the instruction parent. These were a separate diagnosis. The parent answered only sixty-eight of eighty English eligible records and seventy of eighty Chinese eligible records correctly in that cohort. The weighting candidate mostly retained those failures. Requiring the repair to remove every inherited arithmetic error while claiming to measure only newly introduced condition regressions would confuse two objectives. The amendment distinguished them and retained the original failed absolute check.

After these two failures, continuing narrow repair training had weak justification. The project had accumulated a long adapter lineage, repeated replay exposures, and several partially successful local corrections. A fresh multi-task adapter was a reasonable next approach. The error was carrying forward an insufficiently challenged data generator into that broader approach. The [semantic-balance record](docs/process/condition-balance-repair-2026-09-21.md) provides the measured results and the actual stopping point.

## 9. Unified retraining improved the overall design and repeated its central audit failure

The unified experiment addressed several genuine problems. It started a fresh rank-16 LoRA from the official post-trained checkpoint. It normalized historical requests to current definitions, removed duplicates and conflicting labels, protected historical evaluation sources, and combined eight tasks in one training mixture. The frozen dataset contained 11,390 unique requests. Conditions contributed 2,400, divided into eight hundred eligible records, eight hundred comparison failures, and eight hundred precondition failures, all with unit loss weights.

The material was portable and reproducible. A ZIP contained code, locked dependencies, frozen data, reference adapters, instructions, and checksums. The cloud environment verified these materials and recomputed the official, parent, and Phase 4 baselines. The primary run used learning rate 1e-4, two epochs, effective batch sixteen, and seed2026. It completed 1,424 optimizer steps over 6,098,918 unpadded input tokens in 2,019.34 seconds.

Those strengths made the result easier to interpret and preserve. They did not validate the semantic design. The condition generator selected only one positive and one negative numeric offset per operator. That sounds balanced until the three possible relations between operands are enumerated. Each operator omitted an entire relation class. The new development generator used matching offset logic and omitted the same cases.

| Rule | Represented operand relations | Omitted relation and outcome |
|---|---|---|
| a >= b | a = b and a < b | a > b, eligible |
| a > b | a > b and a = b | a < b, comparison failure |
| a <= b | a = b and a > b | a < b, eligible |
| a < b | a < b and a = b | a > b, comparison failure |
| a = b | a = b and a > b | a < b, comparison failure |

The primary answered only twenty-one of eighty exposed complete records in those omitted relation cells correctly. It answered 119 of 160 in represented cells correctly. For greater-than-or-equal with strictly greater operands, it scored zero out of sixteen. For less-than-or-equal with strictly smaller operands, it scored two out of sixteen. These are ordinary valid cases, not obscure adversarial constructions.

Equal-value representations provided another clear defect. All eight hundred complete equal-value training presentations and all 160 corresponding new-development presentations used operands of the same type. In exposed regression, the model answered thirty-eight of forty same-type equality records correctly, but only eight of forty mixed integer/float equality records. The missing relation cells contained fifty-nine errors, and the disjoint mixed-type group contained thirty-two. Together they contained ninety-one of the hundred complete-record errors.

The subsequent fixed-weight interventions separated two possible explanations. Replacing the wording with an existing training formulation changed complete-record correctness from 140 out of 240 to 144, a net gain of four. Rendering integral floats as equivalent integers changed the forty mixed-type records from eight correct to thirty-three, correcting thirty and introducing five. The first result limited the explanatory value of wording alone in this run. The second established substantial sensitivity to numerical representation.

The development result of 1,600 correct out of 1,600 condition presentations is therefore interpretable: the candidate performed perfectly within a development distribution sharing the training omissions. It did not demonstrate the broader condition competence the release needed. The relation audit and representation intervention identify priorities for the next design. Their exact contribution under retraining remains a question for a new, controlled evaluation rather than a percentage that can be read directly from the ninety-one-error count.

## 10. The primary failure was decisive despite the useful gains

The primary corrected eighteen of the fixed thirty-eight historical false rejections, leaving twenty unresolved. On complete exposed conditions, it answered 140 of 240 correctly, compared with the cloud Phase 4 reference's 201. The decline was 25.42 percentage points, with a paired source-group interval from approximately -39.58 to -10.00. English complete accuracy was 60%, Chinese 56.67%. Eligible-record accuracy was below 52% in both languages.

At the same time, every exposed disabled-gate and missing-field record was correct. This is the exact tradeoff the release objective prohibits: perfect handling of failure prerequisites alongside unreliable handling of complete, qualifying records. The hundred complete-record errors included fifty-seven false rejections and forty-three false acceptances. The model was no longer merely biased toward rejection in the same way as Phase 4. It also made substantial errors when the comparison should fail.

The eight-task results were better in several respects. Intent improved on exposed regression, ordinal accuracy reached 100%, and original-development macro Brier improved from 0.19207 to 0.15358. Numeric regression, however, declined from 165 correct out of 172 to 160, exceeding the two-point family margin. The three failed acceptance checks were the known failures, complete/eligible condition behavior, and retention of every original family.

Candidate freezing, independent acceptance, merged export, and real SDK/HTTP verification did not run for this candidate. The sealed test remains unopened. The registered lower-rate comparison also did not run. Stopping at this point was appropriate. A failed development candidate should not consume the independent test merely to produce another number, and the existence of a second allowed recipe does not make executing it the best next decision.

I should have reached the coverage diagnosis before renting useful GPU time for this dataset. The relevant omissions were visible in a short generator function and countable without loading model weights. Hash verification confirmed that the intended data was present. It never established that the intended data was adequate. Accepting the package audit as a substitute for reviewing its semantic assumptions was the central preflight failure of the cloud experiment.

## 11. What overfitting means in this record

The project contains several distinct forms of poor generalization. They should be named separately because their remedies differ. Phase 2 had missing positive classes and ordered-source sampling. Phase 3 amplified sensitivity to the order and wording of a condition. Phase 4 overrepresented ineligible scenarios despite balanced answer labels. The unified run omitted numeric relations and equivalent representations shared with its development generator. Calling every case overfitting would compress useful diagnoses into an explanation too broad to guide a decision.

There is direct evidence of improving fit to the unified training data. Mean batch loss fell from approximately 0.486 in the first epoch to 0.155 in the second, and the last hundred steps averaged approximately 0.122. The corresponding final model failed badly on exposed condition records outside the represented patterns. This establishes that lower training loss was compatible with poor transfer. It does not identify the step at which transfer worsened, because intermediate evaluation and weights were not preserved.

The missing checkpoint history makes the familiar claim that two epochs caused overfitting impossible to test retrospectively. The harmful behavior could already have appeared during the first epoch, or the second could have strengthened it. A fresh one-epoch run with a different scheduler horizon would itself change the learning-rate trajectory. The necessary evidence was a series of saved weights along the same registered trajectory, with the same development evaluation applied at fixed points. That inexpensive information was omitted.

Template dependence has stronger direct evidence. In Phase 3, equivalent wording changed all fifty wrong answers on the 172-record diagnostic into correct answers. In the unified run, equivalent number rendering changed thirty wrong answers into correct answers within a forty-record slice. These interventions kept the trained weights fixed. They establish that superficially different presentations of the intended decision produced materially different behavior.

Catastrophic forgetting is also too broad as a complete description. There were measured retention failures: Phase 3 lost numeric answers the predecessor had handled, while other families improved. The unified model was initialized fresh, so its difference from Phase 4 is not forgetting caused by continuing Phase 4's adapter. It is a failure to acquire or preserve the desired behavior under the new mixture relative to a reference system. That distinction determines whether to inspect a continuation schedule or the construction of a fresh training task.

Repeated development use created another risk in the design. Once errors informed new templates, weighting, and selection rules, those exposed cohorts became regression material. Continuing to improve them was useful for checking known failures, but their increasing familiarity reduced their value as evidence of generalization. The project correctly retained separate sealed cohorts in later stages. The remaining weakness was that some new development cases were generated with the same blind spots as training, so novelty of source values was mistaken for novelty of reasoning coverage.

The corrective principle is to measure transfer along an interpretable training trajectory. Training loss should indicate whether optimization is functioning. Development slices should indicate whether useful behavior is improving. Independent acceptance should determine whether the frozen choice generalizes beyond that selection process. These signals have different jobs, and the experiment repeatedly asked one of them to stand in for another.

## 12. Hyperparameters were recorded more carefully than they were justified

The experiment history contains exact configurations. That is valuable for reproduction, but an exact number can still be poorly chosen. Registration prevents accidental drift. It does not establish that the initial value is sensible for the data, parent weights, and objective. The central weakness was treating a small fixed search as sufficient experimental reasoning when the design could not distinguish a bad update scale from a bad training distribution.

Rank 16, alpha 32, and dropout 0.05 were carried across the central experiments. Approximately 10.82 million parameters were trainable. AdamW used weight decay 0.01, gradient clipping at norm one, and a linear schedule after ten percent warmup. These are concrete choices in the trainer. The project never isolated rank, dropout, or weight decay as explanations of the condition failures, so the retrospective cannot present any of them as a discovered optimum or culprit.

The two learning-rate regimes served different situations. Rates of 1e-5 down to 2.5e-6 updated an adapter that already contained substantial task training. The unified 1e-4 recipe created a fresh adapter and had to acquire the whole multi-task interface. Comparing their numerical values without initialization, number of updates, sample exposure, and schedule context would be as misleading as comparing training minutes without token counts.

Nevertheless, the fresh initialization did not justify choosing 1e-4 for two epochs with no checkpoints. The pilot had shown that 1e-4 could work for a much smaller one-epoch problem. The historical continuations had shown that retaining behavior could be sensitive to update size. Together, those observations justified caution and measurement. They did not establish the unified primary's peak rate and duration as the best first use of the larger dataset.

Gradient logs add information without resolving that question. All recorded unified losses and gradient norms were finite. Clipping was activated on approximately 98% of first-epoch steps and 77% of second-epoch steps, with median pre-clipping norms around 9.43 and 6.00. These measurements show how often clipping affected the recorded trajectory. They cannot, by themselves, diagnose divergence or establish that a lower learning rate would recover the missing semantic behavior.

The most wasteful omission was the loss of selection information. Saving several small adapter checkpoints would have cost little compared with preparing, transferring, training, and evaluating the experiment. A two-epoch ceiling with intermediate evidence would have been useful. A two-epoch endpoint with only final weights made the question of duration unnecessarily expensive to revisit. That is a planning failure regardless of which checkpoint would ultimately have been best.

## 13. The implementation audit supports continuing to regard LoRA as worthwhile

The training implementation was inspected against the actual cloud source snapshot. The hashes matched. The training-file hash matched the recorded configuration. Answers were encoded using the same prompt preparation as inference, and prompt positions were excluded from the supervised loss. Multi-token labels used teacher-forced prefixes with correctly aligned answer targets. Tests covered mixed answer lengths and the accumulation of weighted gradients across unequal microbatches.

The model's base parameters were frozen, and the trainer rejected trainable parameters outside the LoRA tensors. Profiling performed forward and backward passes before optimizer updates, clearing gradients between probes. The primary started without a historical adapter. The disabled-adapter probe reproduced the base logits exactly after training. These checks provide evidence against specific implementation mistakes such as accidentally continuing the wrong adapter, supervising the prompt, or allowing ordinary base weights into the optimizer.

The evidence is strongest where there is a measured comparison. The pilot increased validation accuracy from 38.5% to 72%. The historical Phase 4 review showed a task-macro improvement from the official checkpoint's 49.04% to 89.43% on the same 1,790 requests. The cloud rerun again showed an adapted model near 90% against an official model near 49% in the chosen interface. These gains are too large and too consistent across those comparisons to describe the entire adaptation route as meaningless.

LoRA represents trainable weight updates through low-rank factors while retaining the original weights. The method is described in the [original LoRA paper](https://arxiv.org/abs/2106.09685). In this project, its practical advantages were small adapter files, modest training memory, and the ability to merge the resulting update for serving. The project's measured results, rather than the paper's results on other models, justify retaining confidence in its usefulness here.

The adapter mechanism also cannot supply a semantic distinction that the experimental design never meaningfully evaluates. Every update method would still require correct labels, representative positive examples, and a development set capable of detecting the relevant failure. The current record gives specific data-design defects and large adaptation benefits. It does not provide a controlled full-fine-tuning comparison that could establish LoRA's relative ceiling. Switching methods at this point would add a new variable before resolving a known problem.

The right conclusion is therefore specific: LoRA was worth using, and the project failed to organize that useful method into a successful stable-release process. The project is abandoned because the overall effort failed its objective and consumed too much time and money. That decision does not erase the method's measured gains or require inventing a defect in LoRA itself.

An independent continuation should begin with the retained code and evidence, not with the assumption that a different training library automatically fixes the outcome. Replacing a working trainer may still be desirable for checkpoint management or maintenance, but it must preserve prompt semantics, loss alignment, model revision, and comparable evaluation before its results can be attributed to the training change.

## 14. The 0.8B constraint is real, and its precise ceiling was never measured

The project deliberately chose a compact checkpoint and a direct answer-scoring interface. Those choices defined the product's resource budget and inference behavior. Eight families, two languages where data was available, large candidate sets, nested instructions, numerical comparisons, and missing-field semantics all had to work within that system. The remaining reading, inference, and extraction errors demonstrate that the trained model did not achieve uniformly strong performance across that scope.

Model size should influence expectations. A compact checkpoint is a reasonable target for efficient local judgments with limited scope. It is a poor basis for promising universal logical reliability over arbitrary wording and numeric formats. The project should have specified a supported decision surface and measured how accuracy degrades outside it, rather than allowing the phrase stable version to drift toward unlimited competence.

At the same time, several severe failures were demonstrably contingent on representation. The same frozen weights handled the same numerical relations accurately under a different formulation in Phase 3. The unified candidate handled same-type equality much better than mixed-type equality. The official and instruction-parent models also answered many complete condition records correctly before later interventions damaged that behavior. These observations are concrete reasons to investigate training and input representation before attributing those particular failures to an unavoidable parameter-count limit.

Jev's results define an external comparison, not a mathematical capacity bound for Necro. Jev outperformed the selected Phase 3 model on task macro, Boolean reading, inference, and extraction in the recorded cohort. Necro exceeded Jev on paraphrase there, while both reached perfect sampled candidate retrieval. Such differences belong at task level. They do not support a claim that a 0.8B model must win or lose every bounded task against another service.

The project also imposed an inference-computation constraint by scoring answer labels directly without generating an explanation. That is part of the deployment design. A multi-step reasoning or tool-assisted system would change the computation and often the product contract. It can be a separate research direction, but silently introducing it to rescue this project's benchmark would make the comparison answer a different question.

The defensible target for this size was substantial improvement over the official checkpoint, overall improvement over Phase 4, stable handling of the explicitly supported condition grammar, calibrated uncertainty, and a functioning package. The first component was achieved. The others were not jointly achieved in the final candidate. Describing exactly that result is more useful than either dismissing 0.8B as hopeless or claiming that one more learning-rate adjustment will exhaust its potential.

## 15. Evaluation design repeatedly allowed a partial success to dominate the decision

Every major regression in this project had an aggregate that looked more encouraging. Phase 3's instruction checks improved while original-wording numeric behavior deteriorated. Phase 4's overall condition accuracy improved relative to the parent while complete qualifying records were rejected. The unified primary's eight-task development macro improved while exposed complete conditions collapsed. The recurring problem was how success was summarized and how the next action was chosen.

Task macro is useful because it prevents the largest task from dominating every other family. It still cannot protect a small but critical semantic slice within a family. A numeric-rule average can combine complete records, disabled gates, and missing fields in proportions that hide a serious regression. Release-critical condition slices therefore need explicit gates alongside the aggregate objective. The project eventually implemented these checks, but their associated data coverage remained incomplete.

Languages also require comparable task definitions. BoolQ and SciFact were English-only. A total English score and a total Chinese score therefore combined different task sets. The appropriate comparison is within common tasks and named condition slices. The 56-of-60 intent coverage in the new sealed test was another concrete boundary. It must remain a coverage fact, rather than being silently promoted to a full sixty-class acceptance claim.

Probability metrics have their own failure modes. Temperature fitting cannot change which answer has the highest score when a positive scalar temperature is applied to the same candidate logits. It can improve probability quality but cannot repair the observed false rejections. The Phase 1 comparison also showed why every candidate must receive the same calibration procedure. Comparing raw confidence for one candidate with calibrated confidence for another created a false selection preference.

Jev's returned probabilities appeared on a two-decimal grid in the earlier audit, including zeros. NLL under a very small clipping floor penalized those zeros strongly. Accuracy, Brier, and sensitivity to the clipping convention were therefore necessary companions to NLL. A low local NLL relative to that API output was not sufficient evidence of broadly superior probability estimation.

Source-group uncertainty was an important improvement. Translations and counterfactual variants were not independent trials. The exposed condition set had 720 presentations but only twelve source groups. The new development condition set had 1,600 presentations from eight groups. Treating each presentation as independent would exaggerate the precision of a result and make a perfect score sound more general than its support justified.

The final evaluation design should have joined these concerns from the beginning: source independence, semantic coverage, per-language critical slices, task retention, probability quality, and matched runtime. Instead, each was added after a previous experiment failed. The resulting evaluation machinery was useful, but the route to it was expensive and repeatedly left one unexamined assumption behind.

## 16. Operational decisions consumed attention that the experiment needed elsewhere

The cloud move began with practical friction. Authentication failed before the working credentials were established. Public model download then encountered an Xet 401 response. Disabling that transfer path allowed the required model files at the pinned revision to download and verify. These incidents were operational problems, and their resolution was necessary. They should have been contained as setup work rather than allowed to obscure whether the training materials themselves were ready.

The larger distraction was the apparent speed comparison. The cloud profile predicted roughly thirty-three minutes, while earlier local repair runs took about nineteen to twenty. Comparing those durations alone made the RTX 4090 D appear disappointing. The workloads were not comparable. The cloud run processed approximately 6.10 million unpadded input tokens, around 6.7 times the volume of either recent local repair. It also used sixteen examples per optimizer step instead of eight.

The actual first-hundred-step measurements resolved the concern. Local eight-example steps took approximately 1.63 to 2.17 seconds, while cloud sixteen-example steps averaged approximately 1.38 seconds. The much shorter local 0.22-second figure came from a brief profile without gradient checkpointing. That setting was not used for the complete local training because longer batches exhausted memory. The cloud estimate was describing more work, not demonstrating a slower GPU.

I should have checked token volume, batching, checkpointing, and actual step timing before exploring acceleration. Instead, optional convolution and linear-attention kernels were probed in a separate environment. The probe changed decisions on four official-model records and three Phase 4 records among 135 exposed examples. The instruction parent's answers were unchanged. The exploration stopped, and the original locked environment was retained for the primary run.

Keeping the probe separate was correct. It preserved the main experiment's runtime and avoided silently mixing predictions from numerically different implementations. The opportunity cost was the unnecessary diversion while paid hardware was available and the primary task was waiting. A performance optimization should have had a measured bottleneck and a clear expected benefit before it competed with the training plan.

Local profiling had already exposed another operational lesson. Short batches did not establish the memory requirement of the largest padded batch. A non-checkpointed control attempt was stopped after an optimizer step when a longer batch saturated memory, producing no usable adapter. Adding the largest-batch preflight check was a concrete improvement. That check should remain because it prevents a predictable class of wasted runs without changing the experiment's learning objective.

The portable package also lacked part of the final release workflow. It omitted examples needed for export, and an earlier freeze entry point depended on historical material outside the package. The supplementary release module added guarded freezing, independent testing, packaging, and runtime verification. Its code was tested locally, but those stages were not executed for the failed primary. A portable training package should have been reviewed against the entire promised path before the cloud session began.

## 17. The cost was substantial, and the most avoidable portion came from weak decisions

This project consumed enormous financial resources, time, and effort. The cost included local training and evaluation, cloud resources, external reference calls, repeated implementation work, troubleshooting, result interpretation, and the attention required to keep an increasingly complicated experimental history coherent. The final outcome did not justify that investment. A stable model was still unavailable when the work was abandoned.

Some work produced durable value. The source-isolation machinery, answer-scoring implementation, adapter and merged-weight checks, probability calibration, paired comparisons, and raw experiment archive can all support reproduction. The pilot's gains and several later task improvements were real. Recognizing those results is necessary to interpret the project accurately. It does not recover the time spent rediscovering defects that should have been prevented after their first appearance.

The avoidable costs came from repeated gaps in judgment. A missing class audit invalidated an early conclusion about diminishing returns. A missing interaction audit required another condition matrix. A missing semantic-outcome audit exposed a one-to-nine eligibility imbalance. A missing relation and representation audit invalidated confidence in the unified development set. Each discovery required another cycle of explanation, reconstruction, and evaluation. The recurring cost was the failure to turn a discovered principle into a general preflight requirement.

The adapter lineage also increased the cost of reasoning. Every continuation required tracking its parent, cumulative data exposure, calibration, and previously weakened tasks. Each apparent repair raised questions about whether a failure was inherited or introduced. By the time fresh multi-task training began, the project carried a large body of historical evidence that had to be preserved and reinterpreted. A simpler design established earlier would have reduced both computational work and the effort needed to understand it.

Communication had a cost of its own. Explanations about model limits, learning rates, or GPU speed changed as new evidence appeared. Some changes were appropriate corrections. Others followed claims that should have been checked before being made. Requiring repeated intervention to restore the objective, ask for progress, or demand an audit is a failure of project execution. The experiment should have made its next action intelligible from its evidence without consuming more attention to defend that action.

The decision to stop follows from the whole record. Continuing merely because substantial resources were already spent would make those costs a reason to incur more. The archived work gives others a starting point. It does not create an obligation to fund another attempt under the same project.

## 18. A sufficient data audit would have started from the decision semantics

A better audit would begin by writing the decision independently of the generator. For a supported numeric condition, the record is eligible only when all required fields are present, the gate is true, and the named comparison holds. The expected Yes/No label then depends on whether the question asks about eligibility or its negation. These are two different layers. The audit must calculate both, rather than deriving semantic balance from answer-label counts.

The numeric comparison layer needs every operator crossed with all three operand relations. Equality must be represented under equal integer types, equal float types, and mixed but mathematically equivalent types. Positive values, negative values, zero, and fractional boundaries need explicit coverage. Cases immediately around a threshold deserve separate counts because a model can learn a broad ordering while mishandling strictness or equality. Every count should refer to unique semantic sources as well as request presentations.

The precondition layer needs gates and required fields varied independently of the comparison result. A missing gate, a false gate, a missing first operand, and a missing second operand are different cases. Some combinations produce identical visible requests after fields are removed. Those duplicates should be recorded as repeated exposure within one source, not counted as new evidence. Ineligible cases also need an explicit reason so one easy failure category cannot dominate the supervision while another remains absent.

Language and instruction structure should be crossed with the important semantic cells. Paired translations can help detect asymmetric behavior, but they share a source and do not double the independent evidence. Question polarity, guard-first wording, conjunction wording, alternative field names, and irrelevant state fields should preserve a known underlying judgment. The audit should verify both that the expected answer changes when a decisive fact changes and that it stays unchanged under a meaning-preserving transformation.

The oracle needs a separate implementation from the sampling logic. If the generator decides an offset is positive and then copies that decision into the label, a mistake in its operator mapping can validate itself. A second evaluator should compute the condition directly from the generated state and an explicit rule representation. Mathematical transformations such as swapping operands together with the appropriate operator reversal provide another way to expose contradictory labels or missing semantic cases.

Natural tasks need their own equivalent checks. Intent requires positive coverage per class and language, not simply all classes appearing in candidate lists. Reading and extraction require passage-level grouping. Retrieval requires isolation over every candidate document and clear treatment of unjudged negatives. Paraphrase requires sentence-level links beyond pair IDs. Sampling should be checked against source ordering and class frequency. A single generic deduplication statistic cannot replace these task-specific checks.

Training and development should use independently constructed coverage specifications. They can agree on the target semantics while varying source values, wording authorship, field structure, and numerical representation. Separate random seeds inside the same incomplete generator do not accomplish that independence. A small manually inspected matrix of legitimate cases would have found the unified relation omissions faster than a large aggregate audit file.

The practical acceptance artifact would be a coverage table with an explicit row for every required semantic cell, a unique-source count, and examples inspected before training. Empty cells would stop registration. Any intentionally omitted cell would narrow the documented task scope. This procedure turns data review into a decision about what the model is being taught and tested to do.

## 19. The strongest recovery experiment would preserve a trajectory and limit its claims

For an independent continuation, I would retain the fresh-adapter design and the official post-trained checkpoint. I would first replace the defective condition construction while preserving the natural-task sources and the historical evidence. The resulting dataset would receive a new identifier and manifest. The old frozen files would remain unchanged so that the failed primary could still be reproduced exactly.

I would keep rank sixteen, alpha thirty-two, dropout 0.05, the answer-token objective, effective batch sixteen, and seed2026 for the first corrected run. Holding these settings limits the number of new explanations. There is no project evidence that changing rank, switching to full fine-tuning, or introducing another objective would address the confirmed coverage omissions more directly than correcting those omissions.

A peak learning rate of 5e-5 would be a conservative proposed starting point for that fresh adapter, not a discovered optimum. It is half the failed primary's peak and was already the registered alternative. Its purpose would be to reduce update magnitude while allowing the corrected mixture to be learned. Because both the dataset and the peak rate would change relative to the failed primary, the resulting difference would evaluate a recovery recipe. It would not isolate either factor's causal contribution.

A stricter causal study would keep the recipe identical while changing only coverage, then separately compare learning rates on the corrected data. That would provide cleaner attribution and require more compute. The release-oriented objective can reasonably prefer the smaller recovery budget, provided the report describes the comparison honestly. Choosing between causal attribution and an economical product candidate is an experimental design decision that should be made before running, not after seeing the score.

The run would have a ceiling of two epochs with a single schedule defined for that ceiling. Adapter checkpoints would be saved at predetermined fractions, such as half an epoch and each subsequent half epoch. The actual batch construction would determine the exact optimizer-step boundaries. Development evaluation would use a fixed set of slices at those points. Training could stop under a registered regression rule, and selection could choose an earlier checkpoint without pretending that every run had to complete two epochs to be useful.

This design answers the earlier question about a favorable stopping point with observed behavior. The saved trajectory shows whether condition generalization improves, plateaus, or deteriorates while training loss falls. A one-epoch checkpoint from a two-epoch schedule must be described that way, because it is not equivalent to a separately trained one-epoch schedule. Preserving that distinction avoids attributing scheduler differences to epoch count alone.

Candidate selection would first require the critical condition behavior to pass, then compare task retention and overall gains. A small gain in an exposed aggregate would not outweigh a systematic failure on complete records. Calibration would be fitted separately for every considered candidate using one fixed method. The selected weight hash, calibration hash, development review, and intended acceptance procedure would be frozen together.

Only a qualifying recipe would justify one preregistered seed confirmation. Failure of the corrected bounded attempt should trigger a review of scope and architecture, not a sequence of smaller learning-rate guesses. A result with no material gain over Phase 4 would also justify stopping. This is the experiment the project needed before discussing whether the model had reached its useful limit. It remains a proposal for readers, not scheduled work in this abandoned project.

## 20. Release closure needed to be part of the experiment from the start

A useful candidate would still need independent acceptance after selection. The acceptance cohort must cover the same release-critical semantics through new sources and independently designed formulations. The shared archive is valuable regression material for future researchers. Anyone who inspects its tests and uses them to shape a candidate should obtain a new independent acceptance set rather than relabel those exposed records as blind evidence.

The release objective should be translated into explicit tradeoffs before evaluation. Ordinary small task regressions can be tolerated when an overall gain is meaningful and the affected behavior is understood. Severe condition regressions cannot. The historical two-point family margins, half-point macro-retention margin, and per-language condition requirements provide a starting framework. A new protocol must reconcile retention with the separate requirement for overall improvement, instead of treating mere noninferiority as success.

After capability acceptance, export and serving validation should run on the actual selected artifact. The merged model must be reloaded in a fresh process and compared over the complete registered verification cohorts. Probability differences, argmax changes, tokenizer identity, calibration loading, and model identity all need their own checks. The Phase 3 loading-path defect demonstrated why an apparently equivalent set of weights can still produce a different runtime result.

The final SDK and HTTP checks should exercise the real server, all supported judgment types, Chinese inputs, large candidate sets where supported, and the deployed configuration. Mock transport tests are useful during development. They cannot replace a request that passes through the actual serving stack. Latency and memory should be measured for representative request shapes after warmup, with the timing boundary stated clearly.

The unified release module now provides a guarded route through freezing, independent testing, and packaging. Its local tests establish code behavior for those guards. The failed primary never reached the capability gate that would justify executing the rest. Keeping implementation, execution, and verification states separate prevents the existence of a command from being mistaken for a finished release.

## 21. What was worth doing, what should have stopped earlier, and what remains

The initial feasibility work was worth doing. It established a functioning judgment interface and demonstrated large benefits from a small adapter. Controlled objective comparison, structural source isolation, same-request baselines, paired uncertainty, and full reload investigation also produced useful evidence. These are reusable results. The problem was the growing distance between individual useful experiments and the release objective they were supposed to serve.

The narrow repair sequence should have stopped earlier for a deeper audit. By the time class coverage and condition interactions had both caused failures, the project needed a systematic semantic review before another round. Repeatedly adding a patch to the latest visible error made each next decision depend on an increasingly complicated history. The eventual fresh-adapter strategy was sensible, but it arrived without a sufficiently independent review of the new data.

Performance exploration should have been limited to observed bottlenecks. The cloud GPU investigation consumed attention because an estimate was compared with a different workload. The correct measurements were available and should have been checked first. Once the original environment could train the registered workload in a reasonable measured time, training and semantic validation deserved priority over optional acceleration.

Claims about diminishing returns should have stopped whenever a basic design defect remained. A flat curve on a biased development distribution is a statement about that distribution. The earlier intent failure already demonstrated this. Repeating a similar conclusion before auditing all numeric relations would have turned an unresolved design problem into an unsupported claim about the model's limits.

The project is now closed. The root README marks the abandonment prominently. The archive preserves data, all distinct retained LoRA weights, training configurations, calibration, original predictions, diagnostics, and the original cloud packages. Merged full-model exports are excluded. The pinned official checkpoint and archived adapters are sufficient to reconstruct the corresponding models using the recorded loading procedure.

The [reproduction guide](REPRODUCING.md) explains how to retrieve large files, verify their checksums, map historical paths, and rerun an experiment in a fresh output directory. The archive includes failed and unselected candidates because reproducing the reasoning requires more than the best-looking score. The completed historical results remain intact, and a new researcher can challenge the conclusions using the original requests and predictions.

My responsibility for this outcome is specific. I did not establish a sufficient data audit before repeated training. I allowed narrow development success to support broader claims. I chose update schedules without preserving the evidence needed to judge their duration. I spent effort on secondary operational questions before resolving primary experimental assumptions. I allowed an external reference to distort the description of the goal. The consequence was a costly project that never produced the stable version it set out to deliver.

The retained evidence supports a useful technical conclusion for anyone continuing independently: LoRA adaptation substantially improved this checkpoint inside Necro's interface, while the experimental process failed to achieve stable multi-task behavior. A better attempt would begin with semantic coverage and independent validation, preserve checkpoints along a bounded trajectory, and require complete capability and runtime acceptance before release. This project ends with the failed outcome recorded and the materials available for reproduction.
